# arrdeck-ios

Native iOS app for the services an [arrdeck](https://github.com/mokk/arrdeck)
user already runs: Sonarr, Radarr, Readarr, Lidarr, Prowlarr, qBittorrent,
Transmission, Overseerr, Bazarr, Plex, gluetun, Prometheus and Trakt. The app
talks to each of them itself, so there is nothing else to host. The web app
keeps its arrdeck backend; the two are allowed to differ.

Whatever only a server can do is not in the app: anything that has to run
while the app is closed (push, cleanup rules, sampling the library for trends)
and feeds for other apps (the iCal calendar, the OPDS catalogue). Reading
status, which needs no server, is kept on the device.

## Layout

- `Sources/ArrdeckDirect` — what the arrdeck server's API did, done on the
  device: the data layer's `…API` protocols answered by asking the services.
  The backend's Python, pinned as the `arrdeck/` submodule, is the reference
  for each answer.
- `Sources/ArrdeckData` — the screens' data layer: domain types, the protocols
  the screens ask, and the observable models. No SwiftUI.
- `Sources/ArrdeckAPI` — the domain types, generated by swift-openapi-generator
  from `openapi.json` (types only, no client), which `Scripts/derive-spec.sh`
  derives from the submodule's spec.
- `Sources/ArrdeckKit` — profiles and their Keychain storage.
- `Sources/ArrdeckUI` — SwiftUI views. They compile on macOS too, so type
  errors surface from `swift build`; iOS-only API stays out.
- `Sources/ArrdeckGlance` — what the widgets and the Live Activity read.
- `App/` — the Xcode app target and widget extension, generated with
  [xcodegen](https://github.com/yonaskolb/XcodeGen). It owns the two Info.plist
  keys a service on the LAN cannot work without: the `NSAllowsLocalNetworking`
  ATS exception (plain-HTTP LAN addresses are refused by default) and
  `NSLocalNetworkUsageDescription` (the local-network permission prompt).

A profile is a set of services. Their addresses and keys are kept in the
Keychain under the profile's id.

## Building

The package needs Xcode's toolchain (SwiftUI's macros are not in the Command
Line Tools):

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
swift build
./test.sh       # the spec and localisation checks, then swift test
```

The app:

```sh
brew install xcodegen
cd App && ./generate.sh && open Arrdeck.xcodeproj
Scripts/install-device.sh   # build and install on a paired iPhone
```

The UI tests are opt-in: they run against real services, whose connections
they take as JSON in `TEST_RUNNER_ARRDECK_CONNECTIONS`
(`{"radarr": {"url": "http://10.0.0.5:7878", "apiKey": "…"}}`).
